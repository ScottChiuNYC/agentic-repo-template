# Repository Ecosystem Architecture

This document is the cold-start map for the repositories that together support agent-driven implementation work, reusable C++/Python project infrastructure, and reviewable repository PDFs.

A new developer or AI agent should be able to read this file first, identify the repository that owns a behavior, and follow the correct update path without relying on conversation history.

## 1. Repository roles

### agentic-repo-template (ART)

ART is the agent-facing overlay.

It owns:

- the generated `AGENTS.md` skill router;
- the repository-local CodeBinder PDF skill and publication workflow;
- the CodeBinder builder Docker image definition;
- the immutable GHCR image digest embedded in generated PDF workflows;
- ART-owned PDF review exclusions in `.codebinderignore.d/art`.

ART does **not** own the language/build skeleton of a project and does not own ICC/C2C protocol semantics.

### copier-pypackage-cpp

This template owns the reusable Python/C++ project skeleton.

It owns:

- CMake, Poetry, pybind11, vcpkg and packaging conventions;
- generated build/test CI;
- the Project Skeleton Contract;
- Python/C++ template provenance in `.copier-answers.pypackage-cpp.yml`;
- build/package infrastructure exclusions used only for CodeBinder review PDFs in `.codebinderignore.d/pypackage-cpp`.

It is deliberately independent from ART. A project may use either template alone or layer both templates into the same repository.

### Coding standards ownership

Language Copier templates own their generated project-local coding conventions in the Project Skeleton Contract. ART only routes agents to the generated contract; it never owns or duplicates language policy. ICC adopts these conventions as Project Boundary guidance for generated code-like declarations, while C2C applies them to code, tests and reviews. No mandatory formatter or formatting-only CI gate is part of the default workflow, and no bulk formatting is authorized by a template update.

### implementation-convergence

This repository is the semantic authority for the two explicit implementation workflows:

- Implementation Contract Convergence (ICC);
- Contract-to-Code Convergence (C2C).

It owns the workflow contracts, state models, audit/reconciliation/remediation rules, acceptance derivation, implementation/review/final-verification protocol, and backend semantics.

It does **not** own the downstream project's build skeleton or ART's publication environment.

### codebinder

CodeBinder is the repository-to-documentation-tree engine.

It owns:

- recursive source discovery;
- ignore semantics;
- source-to-notebook conversion;
- generated RST indexes;
- copied assets;
- the optional Sphinx extension used by the PDF pipeline.

CodeBinder does **not** own GitHub Actions publication, Google Drive credentials, the ART Docker image, or downstream template provenance.

## 2. How the pieces compose

A typical implemented project uses two independent Copier overlays:

```text
copier-pypackage-cpp
        |
        | build/package/test skeleton
        v
downstream project
        ^
        | agent routing + PDF publication
        |
agentic-repo-template
```

ICC and C2C are loaded by the generated ART skill router from the canonical `implementation-convergence` repository.

The review PDF path is:

```text
tracked downstream repository
        |
        | .gitignore
        | optional project-owned .codebinderignore
        | template-owned .codebinderignore.d/* fragments
        v
CodeBinder
        |
        v
Sphinx / nbsphinx / LaTeX
        |
        v
validated repository PDF
        |
        +--> GitHub Actions artifact
        |
        +--> optional Google Drive publication on main
```

## 3. Authority and ownership rules

Do not collapse independently owned files merely because they participate in one workflow.

Important ownership boundaries:

```text
.copier-answers.art.yml
    -> ART provenance

.copier-answers.pypackage-cpp.yml
    -> Python/C++ template provenance

.codebinderignore
    -> optional project-owned exclusions

.codebinderignore.d/art
    -> ART-owned exclusions

.codebinderignore.d/pypackage-cpp
    -> Python/C++ template-owned exclusions

docs/development/PROJECT_SKELETON_CONTRACT.md
    -> project-local build/package/layout authority generated by copier-pypackage-cpp

docs/development/essence.md (or another declared Essence)
    -> domain implementation authority after ICC freeze
```

A template should update only the fragment/files it owns. In particular, do not replace the composable ignore-fragment model with one shared generated `.codebinderignore`.

## 4. Review-PDF design intent

The repository PDF exists primarily to review the meaningful result of ICC/C2C work:

```text
contract / audit
    -> implementation
    -> acceptance tests and verification evidence
```

The policy is intentionally exclusion-based rather than whitelist-based:

```text
all new tracked review-relevant material
    - explicitly classified infrastructure noise
```

This is safer than a whitelist because a new substantive source, test, research, or specification directory appears in the PDF by default instead of being silently omitted.

Current template-owned exclusions remove agent/publication plumbing and build/package infrastructure such as workflow files, CMake/vcpkg scaffolding, editor settings, bootstrap scripts and template provenance. Domain source, public headers, bindings, tests, examples, Essence/audit material, and C2C evidence remain reviewable unless a project deliberately adds its own exclusion.

## 5. CodeBinder builder image and dependency pinning

ART defines the builder at:

```text
docker/codebinder-pdf/Dockerfile
```

The Dockerfile pins CodeBinder to an immutable Git commit. The ART image workflow builds the image in GitHub Actions, publishes it to GHCR, emits provenance and an SBOM, and records the resulting immutable image digest.

The generated downstream workflow pins the final image by digest:

```text
ghcr.io/scottchiunyc/art-codebinder-pdf@sha256:...
```

This creates two distinct reproducibility layers:

1. **CodeBinder source identity** — pinned Git commit in the Dockerfile.
2. **Runtime image identity** — pinned immutable GHCR digest in downstream workflows.

The current Dockerfile does not yet pin every Ubuntu or Python dependency to an exact package version. Therefore rebuilding the Dockerfile later may produce a different image, but an already-published digest remains immutable. Exact base-image/Python dependency locking is a separate maintenance improvement.

## 6. Change-propagation playbooks

### CodeBinder behavior change

Use this sequence when CodeBinder behavior used by downstream PDFs changes:

```text
1. change + test CodeBinder
2. merge CodeBinder
3. pin the new CodeBinder commit in ART's Dockerfile
4. build and smoke-test a new GHCR image
5. obtain the new immutable image digest
6. pin that digest in ART's generated PDF workflow
7. validate ART against at least one real consumer when behavior crosses repo boundaries
8. Copier-update ART in downstream repositories
9. verify downstream PDF builds/publication
```

Existing downstream repositories do not automatically receive a rebuilt image because their workflows pin an immutable digest.

### ART-only generated behavior change

For a change to generated ART files that does not require a new builder image:

```text
1. change + validate ART
2. merge ART
3. genuine Copier update using .copier-answers.art.yml
4. inspect exact downstream diff
5. verify applicable PDF behavior
```

### Python/C++ skeleton change

For a reusable build/package/layout change:

```text
1. change + validate copier-pypackage-cpp
2. merge the template
3. genuine Copier update using .copier-answers.pypackage-cpp.yml
4. preserve domain implementation and project-specific changes
5. run applicable build/package validation
```

### Cross-template review-exclusion change

If CodeBinder semantics must change first, use the CodeBinder playbook above. Then update only each template's own ignore fragment and perform genuine Copier updates for the affected overlays.

## 7. Validation boundaries

A unit test in one repository proves only that repository's local contract.

Cross-repository behavior requires a real consumer check when the change crosses a boundary. Examples include:

- CodeBinder discovery/ignore semantics;
- builder-image dependency changes;
- ART publication behavior;
- Copier migration behavior;
- PDF rendering or Google Drive publication.

Do not infer an end-to-end PASS solely from a template unit test.

## 8. Rollback model

Git history is the primary rollback mechanism.

Prefer:

- isolated feature branches;
- focused pull requests;
- squash merges for one logical change;
- immutable image digests;
- exact Copier provenance in each answers file.

A merged focused change can normally be reverted as one commit. For a builder regression, downstream repositories can continue to pin or be restored to the previously known-good image digest.

Do not use mutable container tags such as `:latest` as production authority.

## 9. Cold-start checklist

Before changing a downstream repository:

1. read its `AGENTS.md`;
2. inspect all `.copier-answers.*.yml` files to identify template provenance;
3. read `docs/development/PROJECT_SKELETON_CONTRACT.md` when present;
4. locate the declared Essence and audit/C2C evidence for the domain task;
5. inspect `.codebinderignore` and `.codebinderignore.d/*` before changing PDF scope;
6. distinguish template-owned infrastructure from project-owned/domain-owned content;
7. follow the canonical upstream repository for any reusable behavior rather than patching generated copies ad hoc.

When changing one of the infrastructure repositories, begin with its README and agent instructions, then follow the ownership and propagation rules above.
